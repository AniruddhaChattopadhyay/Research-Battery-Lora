Robust Function Calling for LLM Agents Under Interface Drift Aniruddha Chattopadhyay 1⋆ , Kanishka Halder 1 , and Partha Sarathi Roy 1 Independent Researcher, Bangalore, India studyaniruddha@gmail.com, kanishkahalder@gmail.com, psarathi012@gmail.com Abstract. Tool-using language-model agents depend on descriptions, argument schemas, and candidate tool lists. These interfaces can change after deployment while semantics remain fixed, creating interface drift. We test whether a lightweight, training-free repair layer can recover ro- bustness without retraining. Our method, SchemaShield-Lite, combines schema validation, candidate-set retry for missing tool names, and one- shot constrained repair. On Qwen3.5-9B, it raises DICE-300 accuracy from 0.717 to 0.813 and BFCL-200 accuracy from 0.580 to 0.805, recover- ing 19/22 and 33/45 drift-induced failures with no observed repair harms. Naive retry does not explain the gains. In the Qwen3.5-9B DICE abla- tion, distractor tools cause most damage, while description and schema edits cause less. The results support validation-and-repair as a promising but model-dependent fallback. Keywords: tool-augmented large language models · function calling · interface drift · agentic AI robustness · inference-time validation and repair 1 Introduction Modern language-model agents increasingly depend on external tools for re- trieval, execution, planning, and actuation. In practice, however, tool use is me- diated entirely through text: tool descriptions, parameter schemas, enum values, and candidate tool lists. Recent work shows that these interface details strongly affect tool selection and argument generation even when the tool semantics are unchanged [3,1]. This creates a deployment problem: tool interfaces drift over time as developers rename parameters, revise descriptions, add examples, or expand candidate tool sets. We define interface drift as benign, semantics-preserving interface changes after deployment. Rather than train a new model, we quantify drift sensitivity and test whether compact inference-time repair can recover reliability. We instantiate drift with three deployment-motivated synthetic perturba- tions: (i) stale description examples that mention legacy field names, (ii) schema renaming, and (iii) distractor tools. This paper makes three empirical contributions, demonstrated primarily on Qwen3.5-9B with a supporting replication on Qwen3.5-35B-A3B: 1. A same-protocol BFCL replication on Qwen3.5-35B-A3B (0.635 → 0.845) confirms the effect is not confined to a single model size, though the cleanest non-oracle evidence remains within the Qwen family. 2. Naive retry does not explain the gains. In the separate baseline runs reported in Section 6.2, naive retry reaches 0.727 versus repaired 0.813 on DICE-300 and 0.610 versus 0.795 on BFCL-200. A second attempt alone therefore cannot explain the recovery. 3. Missing tool names are the main non-oracle bottleneck, and most primary-model drift misses remain validator-visible. In the non- oracle setting, adding a candidate-set retry improves repaired accuracy from 0.780 to 0.813 on DICE and from 0.725 to 0.805 on BFCL while reducing unresolved repair targets from 35 to 15 and from 34 to 9 respectively. In the final primary runs, only 2/22 drift misses on the DICE originally-correct slice and 0/45 on BFCL remain validator-invisible. 2 Related Work Recent work has established that tool interfaces are not neutral wrappers around tool use; they are part of the learning and inference problem itself. Guo et al. [3] show that rewriting tool descriptions can substantially improve agent reliability, especially when candidate tool sets are large. Faghih et al. [1] show the opposite direction: small edits to tool descriptions can dramatically shift tool preference, exposing a fragility in description-mediated tool use. Rabinovich and Anaby- Tavor [14] study robustness in agentic function calling under toolkit changes and other perturbations, while our focus is narrower: post-deployment interface drift with fixed underlying tool semantics. Several recent papers study robustness and recovery in tool-use systems. Zhang et al. [20] show that execution-error recovery remains a major weakness, particularly for smaller models, and propose RL-based training to improve it. Our setting is narrower and more deployment-oriented: we target inference-time robustness under interface drift rather than post-training optimization. Our repair stack also connects to structured-output enforcement via con- strained decoding. Grammar-constrained and grammar-aligned decoding study how to guarantee or preserve valid structured outputs during generation [2,10]. We instead study post-hoc validation and repair after the base model has already produced a drifted tool call. Benchmark work has also highlighted that realistic function calling is still far from solved. ComplexFuncBench introduces multi-step and constrained long- context function calling [21], while DICE-BENCH [4] focuses on multi-round, multi-party dialogues with tool-related information dispersed across conversation turns. Other benchmarks, including API-Bank, τ -bench, and ToolSandbox, simi- larly stress planning, state, and interaction in tool-use settings [6,18,8]. We evalu- ate DICE-BENCH and the Berkeley Function Calling Leaderboard (BFCL) [11] as complementary settings. DICE-BENCH exercises conversational multi-turn dialogues; BFCL tests single-turn tool calls across diverse APIs. Broader tool-use work has focused on teaching models to call APIs, retrieving relevant tools, and combining reasoning with action [15,12,13,19]. Our focus is different: robustness when an already-deployed tool interface changes. This setting also connects to software-engineering work on API evolution and contract checking. AutoGuard, for example, compares OpenAPI descrip- tions across versions and flags changes to methods, parameters, responses, and schemas [5]. Serbout and Pautasso [16] study how Web API versioning practices align with the actual changes made across releases. We borrow the intuition that interface evolution is a first-class engineering concern, but study its effect on LLM tool use rather than on conventional API clients. Compared with dataset-generation work such as APIGen [7], our objective is different. We do not create new large-scale tool-calling training data. Instead, we evaluate whether a lightweight repair layer can stabilize existing models against a specific class of post-deployment failures. 3 Problem Formulation Let a tool be represented by an interface I = (d, s, C), where d is the natural- language description, s is the argument schema, and C is the candidate tool set shown to the model. The underlying tool semantics are assumed fixed. An interface drift operator ∆ maps I to a new interface ∆(I) that preserves tool semantics but perturbs surface form. For clarity, we view ∆ as a composition of three operators, ∆ = δ c ◦ δ s ◦ δ d , where δ d edits only the description text d, δ s edits only the schema surface form s, and δ c edits only the visible candidate set C. Each operator is semantics- preserving with respect to the benchmark gold tool call; the evaluation question is whether the model remains robust to these surface-form changes at inference time. We study three drift types: – Description drift: add stale or legacy examples to the description that refer to older field names. – Schema drift: rename parameters while preserving semantics. Given user context x, tool interface I, and model M , the base system outputs a tool call y = M (x, I). We evaluate three stages: 1. Original: inference on the original tool interface. 2. Drifted: inference on the drifted interface ∆(I). 3. Repaired: inference-time repair of an invalid or incomplete drifted call. A repair protocol is non-oracle if it uses only deployment-available user con- text, model output, and runtime-visible tools. An oracle-constrained protocol additionally supplies the benchmark’s gold target tool, which a deployed system would not know; we therefore report such runs only as upper bounds. Our central question is whether an inference-time repair layer can recover the performance lost from Original to Drifted without harming examples that were already correct. 4 Method 4.1 SchemaShield-Lite SchemaShield-Lite is a lightweight inference-time robustness layer with three parts. Figure 1 sketches the full pipeline. Canonical tool card. Each tool is rendered into a compact canonical form contain- ing the tool name, description, required fields, and field-level type information. This normalizes interface presentation across tools and emphasizes current field names. Validation. After the base model emits a tool call, a validator checks tool name, required fields, and argument structure. Validation produces a structured error report rather than a binary failure signal. One-shot repair. If the drifted call is invalid, the model receives a repair prompt containing the task context, canonical tool card, invalid call, and validation er- rors. Under the primary non-oracle protocol, an output that names a visible tool is validated and any repair is constrained to that tool. If the name is missing, the model is first asked to issue a new call from the user context and runtime- visible tool list. A retry that names a visible tool is then validated and, if still in- valid, repaired; a retry without a usable visible name remains unresolved. Where provider support allows it, constrained repair uses forced-tool repair ; otherwise we use unconstrained tool calling or JSON repair. As our component ablation in Section 6.5 shows, it is the combination of structured validation errors and tool-constrained repair that does most of the recovery once a visible target tool has been resolved. The canonical card is useful at the initial prediction step as drift-prevention prompting, but contributes neg- ligibly to repair-stage recovery in our oracle-constrained upper-bound ablations. 4.2 Repair Prompting Details Three implementation details turned out to matter materially in these runs: – The repair prompt explicitly instructs the model to infer all required fields from the dialogue even when the invalid call is empty. – When the invalid call omits the tool name, a candidate-set retry over the visible tools is needed before tool-constrained repair can fire. – The repair stage uses a larger token budget than the base prediction stage. Raising repair capacity from the earlier default to 512 tokens fixed truncated repair outputs on longer DICE dialogues. 4.3 Per-Example Evaluation Loop Each benchmark example is evaluated in three stages: Original, Drifted, and Repaired. Drift is injected once, the gold call is re-expressed in the renamed schema before scoring, and repair fires only when validation flags the drifted call as invalid. We average the three per-example correctness indicators over the benchmark slice to obtain the headline accuracies. 5 Experimental Setup 5.1 Benchmarks and Data Slices We evaluate on two benchmarks. For DICE-BENCH [4], we use a 300-example subset drawn from single-function round-1 dialogues (allowing duplicate func- tions to reach sufficient scale). For BFCL [11], we use a 200-example subset drawn in equal parts from four categories: simple Python, multiple-function, live-simple, and live-multiple. 5.2 Models We evaluate four open instruction-tuned models and one closed model through hosted inference APIs: – Qwen3.5-9B: our primary model. – Qwen3.5-35B-A3B: larger MoE variant. – Llama-4-Scout: Meta’s 2025 open model. – Mistral-Small-3.2-24B: recent Mistral dense model. – GPT-4o-mini: closed-model BFCL sanity check. Full non-oracle runs cover Qwen3.5-9B on both benchmarks and BFCL repli- cations with Qwen3.5-35B-A3B, Llama-4-Scout, and GPT-4o-mini. The retained oracle-constrained DICE sweeps also cover Qwen3.5-35B-A3B, Llama-4-Scout, and Mistral-Small-3.2-24B. All experiments use OpenRouter’s OpenAI-compatible endpoint and tem- perature 0.0, though hosted inference may still exhibit provider-side nondeter- minism. The released configs record the exact model slugs used for each run. 5.3 Drift Configurations For DICE main runs, we use mild severity: two description modes (legacy- example and marketing), two schema modes (rename-parameters and reorder- parameters), and one distractor tool. For BFCL we use medium severity: three description modes, three schema modes, and three distractors, reflecting a more aggressive drift scenario. These operators are author-designed and deployment- motivated rather than mined from real API changelogs; we return to that limita- tion in Section 8. As a limited plausibility check, we manually audited 11 official changelog items from Notion and Stripe spanning 2022–2026. Six resemble our documentation/example and parameter/schema operators, three involve adding or consolidating neighboring tools or endpoints and thus provide candidate- set analogues, and two are larger structural refactors outside our semantics- preserving scope [9,17]. We did not derive the drift operators from these items, and this small purposive audit does not estimate the prevalence or distribution of real API changes. 5.4 Repair Protocols We use two repair protocols. Our primary protocol is non-oracle and is the main evidence in this paper: the validator checks the model-selected visible tool, and when the model omits the tool name, it is asked to issue a new call from the runtime-visible tools. The validator then checks that new call and repairs it only if it remains invalid. For broader model coverage and component ablations, we also retain earlier oracle-constrained upper-bound sweeps in which the repair stage is given the benchmark target tool. These upper-bound runs remain use- ful for cross-model context and ablation, but they are not deployment-facing evidence. 5.5 Metrics We report: – Original score: accuracy on the unmodified interface. – Drifted score: accuracy under interface drift. – Repaired score: accuracy after one-shot repair. – Naive retry score: accuracy under a second identical drifted call (no canon- ical card, no validation feedback). This baseline isolates the value of simply retrying. – Originally-correct slice: the subset of examples that the model solves correctly before drift. This slice isolates true drift harm from baseline errors. – Repair recoveries: drift-induced failures recovered by repair. – Repair harms: drifted-correct examples broken by repair. – Repair-stage invocation rate: fraction of examples that incur at least one post-validation model call, including candidate-set retries that do not resolve a tool name. 5.6 Reproducibility and Release All results use fixed benchmark slices, drift configurations, and evaluation seed 42 for subset and drift selection; hosted inference did not enforce a model seed. Per-run JSON artifacts store example IDs, prompts, drifted schemas, validation outputs, repair targets and strategies, token usage, and the normalized semantic matching policy. We release the code, prompts, configs, subset definitions, scoring logic, and raw artifacts in a public repository (public tool-drift repository at commit fbac156), including example-level traces for the main success and limitation modes. 6 Results 6.1 Primary Non-Oracle Results Table 1 summarizes our primary non-oracle Qwen3.5-9B results on DICE-300 and BFCL-200, together with oracle-constrained upper bounds for reference only. Description drift alone causes only a 0.013 point accuracy drop. Schema drift alone causes only 0.007. By con- trast, candidate-set drift (adding a distractor tool) causes a 0.047 drop, matching the full combined drift scenario (0.050). Because this ablation is about where the damage comes from, the main interpretation still rests on the Original-to-Drifted delta. For the repair column, however, only the distractor-bearing rows require fresh non-oracle evidence. In our DICE-300 slice, every baseline task has ex- actly one candidate tool, so under predicted-tool repair the description-only and schema-only settings collapse to the same effective repair target as the oracle- target protocol via single-candidate fallback. The non-oracle question therefore matters only once distractor tools are introduced. A fresh candidate-set-only non-oracle rerun reaches 0.817, while the primary DICE main run already sup- plies the matching all-combined non-oracle row at 0.813. The qualitative conclu- sion is unchanged: candidate-set drift remains the dominant source of damage in this Qwen3.5-9B DICE-300 ablation, and non-oracle repair stays close to the earlier oracle upper bounds. This result qualifies a common framing in the interface-drift literature. On this Qwen3.5-9B DICE-300 ablation, minor description rewording and semantics- preserving parameter renames do not meaningfully degrade accuracy; the model is robust to these perturbations in this slice. The observed failure mode is candidate-set confusion: when a distractor tool with an overlapping description is added to the candidate set, tool selection degrades. This result motivates test- ing tool-catalog growth separately from description or schema revisions; it does not establish that candidate-set drift dominates for other models, benchmarks, or production catalogs. Re- pair again helps materially, lifting accuracy from 0.635 to 0.845 (exact McNemar p = 4.5 × 10 −13 ). On the originally-correct slice it recovers 33/38 drift misses, shows no observed repair harms, and leaves only one unresolved repair target. This does not eliminate same-family dependence, but it shows that the main BFCL non-oracle effect is not confined to the 9B run. We also ran the same BFCL-200 non-oracle candidate-retry protocol on Llama-4-Scout. Repair still improves over the drifted call (0.635 → 0.665, exact McNemar p = 0.031) and again shows no observed repair harms on the originally- correct slice. However, this run exposes an important portability failure mode: the model omits the tool name frequently, leaving 43 unresolved repair targets and limiting recovery on the originally-correct slice to just 1/11 drift misses. The Llama run therefore supports some portability of the repair effect, but also reinforces that non-oracle repair quality depends heavily on the base model’s ability to emit a usable tool name. We also ran a BFCL-200 non-oracle sanity check on GPT-4o-mini after adding provider-safe tool-name aliasing for OpenAI-style tool schemas. Its drift damage is smaller than in the evaluated open-model BFCL runs (0.865 → 0.840). Repair reaches 0.860 with no observed harms or unresolved targets, but its gain is small and not significant on this 200-example slice (exact McNemar p = 0.125). We therefore treat this as a sanity check, not confirmatory evidence. 7 Discussion Our results support three narrower conclusions than the original SchemaShield- Lite framing suggested. First, in the evaluated Qwen3.5-9B settings, non-oracle inference-time repair improves over drifted performance on both DICE and BFCL while showing no observed repair harms on the originally-correct slice. Second, missing tool names are the main non-oracle bottleneck in these runs; candidate-set retry over the visible tools closes much of the gap to the oracle upper bound. Third, candidate-set drift causes a larger accuracy drop than de- scription or schema drift in the Qwen3.5-9B DICE-300 ablation. These findings identify a compact recipe to test in deployment: visible-tool validation, candidate-set retry for missing names, and constrained repair once a tool is resolved. It recovers most observed damage without the canonical card in the repair prompt. The Qwen3.5-35B-A3B replication works at a second size within the family; the weaker Llama-4-Scout result cautions against assuming cross-family portability. These same results also matter for adversarial interface manipulation. Faghih et al. [1] show that small description edits can steer tool selection even when semantics are unchanged. Our Qwen3.5-9B DICE-300 ablation suggests testing description overlap together with candidate-set expansion: in that slice, routing degrades once distractor tools enter the visible set. Whether the same validator- plus-repair stack helps against adversarial tool confusion requires a dedicated evaluation. 8 Limitations Several limitations remain. First, the strongest non-oracle evidence is concen- trated in the Qwen3.5 family: Llama-4-Scout is bottlenecked by missing tool names, GPT-4o-mini is only a sanity check, and broader model results are mostly oracle-constrained. Second, the author-designed drift operators cover stale de- scriptions, renamed fields, and distractors, not type narrowing, enum replace- ment, or multi-tool refactors; the small changelog audit is not a mined change distribution. Third, the drift-type and component ablations are upper bounds and may not transfer when non-oracle tool resolution fails. Fourth, hosted in- ference may add provider-specific behavior. Although DICE is multi-round and BFCL includes multiple-function categories, we score each example rather than execute sequential tool plans; compounding recovery and production-scale cat- alogs remain untested. Fifth, baseline patching complicates drift-specific attri- bution, while strict matching is conservative: 11/13 inspected misses on non- primary models are formatting or paraphrase artifacts (Section 6.6). Finally, the 32.6%–47.1% token overhead and one-run latency estimate are meaningful costs, but systematic latency and API-cost comparisons across providers, models, and pricing schemes remain future work. 9 Conclusion We studied SchemaShield-Lite, a training-free inference-time validation-and- repair stack for tool calling under interface drift. With Qwen3.5-9B, the non- oracle protocol raises DICE-300 accuracy from 0.717 to 0.813 and BFCL-200 accuracy from 0.580 to 0.805, with no observed repair harms on either originally- correct slice. Three findings qualify the picture. A naive-retry baseline does not explain the gains. Description and schema drift cause only small degradations on the Qwen3.5-9B DICE-300 ablation, where candidate-set drift causes the largest drop. In the primary non-oracle runs, missing tool names are the main repair bottleneck, and candidate-set retry substantially reduces unresolved cases. The headline improvements combine drift recovery with baseline patching: of 29 DICE gains, 19 recover drift-induced failures and 10 patch baseline failures; of 45 BFCL gains, 33 are drift recoveries and 12 are baseline patches. A same-protocol BFCL-200 replication on Qwen3.5-35B-A3B (0.635 → 0.845) reproduces the ef- fect within the Qwen family, but Llama-4-Scout exposes a missing-name porta- bility bottleneck. On GPT-4o-mini, the repair gain is small and not significant on the 200-example BFCL slice (0.840 → 0.860, p = 0.125). The paper should therefore be read as a controlled study of drift sensitivity and inference-time repair rather than as a complete account of production interface drift. Broader impact. The same repair stack that recovers benign drift could in prin- ciple mask adversarial tool injection, where a malicious distractor tool is added to the candidate set. Practitioners deploying inference-time repair should pair it with provenance checks on newly added tools. GenAI disclosure.
